## 1. Scope

- **In-scope (to build):** all 12 decided-behaviour groups in `design-handoff.md` §1 — analysis templates, scheduling, sample/analysis lifecycle, data capture & instrumentation, validation & exceptions, calculation & calibration, result management (review/locking/unlock), search & history, integration & data flow (Databank/SCADA/Lakehouse, with explicit exclusions), cross-site transfer, the Angular+Kendo UI, and the security/auth foundation. Plus the 26 cross-cutting gap items (W1–W26) — scaffolding, state machines, RBAC, persistence wiring, pagination, observability, accessibility.
- **Deferred / vNext (labelled, not built):** reagent/consumables tracking, external-lab-certificate attachment/storage, extended in-LIMS reporting, equipment service reports/certifications (`design-handoff.md` §3).
- **Honest stubs (labelled in product & spec):** none planned for v0.1.0 — every in-scope item below is built to real infrastructure, not a stub. If a task must ship partial during build, it is labelled per the convention established in Task 1 (`FidelityLabel`), never silently.
- **Explicitly excluded, not stubbed:** external laboratory analysis result capture and Factory Data capture (SCADA/ProcessNet/Citect) — these have **no endpoint at all** in LIMS Control Lab, per `brief.md` R56. Task 14 includes a negative test asserting this.

## 2. Reference slice *(build first, correctly, as the copy template)*

**Sequencing decision (operator, 2026-08-25): all backend work completes and is tested before any Angular frontend work starts.** This reorders the backlog into two blocks — Tasks 1–14 (backend, ending in an explicit verification gate) then Tasks 15–22 (frontend) — rather than the framework's usual interleaved-vertical default. This is a deliberate build-strategy choice, not a Definition-phase decision, so it lives here rather than in `charter.md`. It is workable specifically *because* `engineering-standards.md` §4 already commits to an OpenAPI-first contract (Angular's API types are generated from the running API, never hand-mirrored) — the frontend builds against a contract that's already been exercised by backend tests, not a moving target. The tradeoff, worth naming once: backend API shapes get validated by backend tests and manual/API-client inspection only, not by a real UI, until Task 16 — if a screen's real needs demand an API change, that change lands after the "backend done" milestone rather than during it.

**Within each block, still build the reference slice first, correctly, as the copy template** (lesson L-Modernization): Task 3 is the backend half of **"capture a manual reading against a scheduled analysis, validate it against tolerance, and flag/resolve the resulting exception"** — the smallest slice exercising the lifecycle state machine (D1), server-side RBAC (E1–E3), audit trail (D3), and optimistic concurrency (charter §2) all at once, so every later backend task copies its pattern. Task 16 is that same vertical's frontend half, built once the backend block is verified, as the copy template for every later frontend task. `/ship:shape` fixes both halves' exact technical shape before build starts on each.

## 4. Per-slice definition of done

Every task above must meet, before it counts as done (from `engineering-standards.md`):

**Backend:** layered (Controller→Service→Repository) · DTO-mapped, never returns entities · request validation with the standard error shape · server-side RBAC (role + site) matching the UI · paged if it lists · indexed/constrained per `engineering-standards.md` §3 · concurrency-safe (409 on conflict) if it touches a locked/derived value · structured logging + audit entries.
**Frontend:** feature-scoped, standalone Angular components · built on Zard UI primitives + Tailwind v4 *(amended 2026-08-26, charter §3b/A1 · shape C18; was Kendo UI)* — extend the generated Zard component in `shared/components/` before hand-rolling an equivalent · reactive forms mirroring backend validation · typed API service (no raw `HttpClient` in components) · error/loading/empty/permission states handled · WCAG AA.
**Both:** shared-helpers inventory checked/updated (calibration/formula logic especially — this domain is calculation-heavy, per `engineering-standards.md` §6) · tests green across the tiers in `engineering-standards.md` §2 (service tests, HTTP round-trips, an authz-attribute test, a concurrency test, Angular unit/integration tests, one E2E smoke pass).

## 6. Risks & dependencies

- **Backend-first sequencing (operator decision, 2026-08-25):** Tasks 1–14 (backend) complete and pass Task 14's verification gate before any of Tasks 15–22 (frontend) start — a deliberate deviation from the framework's usual interleaved-vertical default, made viable by the OpenAPI-first contract (`engineering-standards.md` §4) generating the Angular client from an already-tested API rather than a moving target. The residual risk: a UI-driven need for an API change surfaces only from Task 16 onward, i.e. after Task 14's gate — treat such a change as a normal new backend task (re-open Task 14's gate for the affected endpoint), not as a reason to have skipped the gate.
- **No existing LIMS platform codebase is available to this project** (confirmed with the operator at audit time) — charter's "extend the existing platform" decision (shared `cane-db`, shared infra) cannot be cross-checked against the real schema, API surface, or auth wiring until that access exists. This is the single biggest integration risk carried out of Design & Handoff; Task 3's migration and Task 5's auth wiring are best-effort against the *documented* architecture (HLD diagrams) until real access is available.
- **Version currency:** .NET 10, Angular 21+, and ~~Kendo UI v23~~ **Zard UI + Tailwind v4** *(amended 2026-08-26, charter §3b/A1)* were the operator's explicit choices (charter §2/§3b) — confirm actual package/tooling availability and mutual compatibility, since no code has exercised this combination yet. Tailwind v4's Angular integration is via `.postcssrc.json` (`@tailwindcss/postcss`), auto-detected by `@angular/build`.
- ~~**Kendo UI license**~~ **License provisioning — no longer applicable** *(amended 2026-08-26, charter §3b/A1)*. The move to Zard UI (MIT, copied into the repo) + Tailwind (open source) removes the only per-environment licensed dependency; `docs/telerik-license.txt` is removed and no UI-library secret needs provisioning to developer/CI/deploy environments.
- **Interim authentication is a stated security-sensitive interim state**, not a target architecture — charter records an Entra ID SSO migration path; this plan does not build that migration, and it should be prioritized in a near-future release rather than left indefinitely.
- **Incremental site rollout** (BRD constraint: "must support incremental rollout across sites") is not sequenced in this plan — v0.1.0 builds the core system for all 8 sites at once; a phased site-by-site go-live is a release-planning decision for a later cycle, not a v0.1.0 backlog item.
- **C Molasses Exchange → Databank routing is provisional** (brief R57) — Task 14 builds the current exclusion; revisiting it in a future release changes Task 14's integration surface, not its Databank-facing contract for other products.
